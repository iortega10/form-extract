(0.6.0). Source: the integrator's `form-extract-0.6.0-feedback.md` (one 17-tab checklist workbook, Haiku 4.5)
plus the reviewer's offline reproductions on an anonymised copy. **The anonymised workbook is a client
document: never open it, never read it, never copy any text from it into the repo, a test, a commit or a
prompt.** Everything below is reproducible from the synthetic shapes described here. A second document,

## What the reviewer verified (offline, scripted replies, no model)

1. **`json` contract: `answers` can contradict the resolver's selection.** With `mark_follows_option` declared
   for a tab, a model reply that selects the wrong option (`answers: ["No"]`, `options: No selected`) for a row
   `label | Yes | X | No` comes out with `options[].selected == ["Yes"]` and `value_raw == "Yes"` (the resolver
   overrode the model, correctly) **but `answers == ["No"]`** (the model's claim kept), `ambiguity` is `None`
   and nothing is flagged. An integrator who reads `answers` gets a confident wrong value. Same on a row
   `label | A | X | B | C` (selected is `A`, the option the mark follows; `answers` is the model's `B`).
   Under `lines`, `answers` stays `[]` and the selection lives only in `options[].selected`: consistent.
2. **Empty `label_text` under `lines`.** `strip_marks` (`layout.py:240`) is applied to each cell cited under
   `L=` (`resolve.py:800-810`), so a label cell that is only a mark (`X`) yields `""`. On a row
   `X | Enforce Unique Policy Numbers` (mark in segment 0, text in segment 1): `bool L=27.1 O=27.0` gives the
   right label; `bool L=27.0 O=27.1` gives `label_text == ""` with the option text carried in `options`;
   `text L=27.0 A=27.1` gives `label_text == ""` and the label text as the *answer*. The field is emitted
   silently with an empty label, which an integrator cannot locate.
3. **The three "0 fields under `lines`" tabs are data tables, not forms** (a one-row header strip, a ~50-row
   lookup table, a small table with two trailing label/value rows). A scripted `text L=4.0 A=4.1` reply on the
   label/value rows bound correctly. The resolver does not drop valid replies; the zero fields were the model's
   `hdr`/`skip` choices. `min_coverage` (opt-in, range (0, 1]) already sets `PARTIAL` below the floor, so
   `min_coverage=0.01` catches ratio-0.0 tabs today. **Do not make "anchors but nothing bound" a default
   `PARTIAL`**: any workbook with a lookup tab would never be `complete`.
4. **Issue 2 is reproduced: a stray mark cell in a TEXT field's row nulls `value_raw` and invents an
   ambiguity.** (Correcting an earlier reviewer note that said it bound cleanly: it binds `answers` but not
   the value.) Row `X | Describe the fee | Administrative charge`, reply `text L=0.1 A=0.2`, glyph `X`, `☒` or
   `✓` alike: `answers == ["Administrative charge"]`, **`value_raw is None`**, and `ambiguity` is set
   (`competing_options` with no convention; `convention_unsupported_by_geometry` with
   `mark_follows_option`). The mark is injected into a TEXT draft that has no options, the mark decision is
   then downgraded to declining, and `value_raw` is nulled before the TEXT branch (`resolve.py` about
   2296-2301 and 2345-2348, per the hearth debate). A SELECT row in the same sheet (`Rounding | Yes | X | No`)
   with the convention resolves correctly (`Yes`). That is the integrator's "value=None at 0.4 beside a
   checkbox", and no prompt variant could fix it because the model's reply was fine.

## What to build

### A. `answers` agrees with the resolver (issue 3). Behaviour change.

Where the resolver's mark decision (`auto_select` or `declared_convention`) sets `selected` flags on a field's
options, the field's `answers` must be consistent with them. Find where `answers` is carried through from the
draft (`resolve.py` around 2270-2330 and the draft-to-Field assembly near 2420) and make the rule explicit:

- if the resolver selected options, `answers` becomes exactly the selected options' texts, in option order;
- if the model's own `answers` differed, keep the model's original under the field's `provenance` (inspect
  `Field.provenance` and use its existing shape; do not add a Field member without reading the next
  paragraph), and set `ambiguity` only if the existing semantics of `ambiguity` fit; otherwise do not
  misuse it;
- if the resolver made no decision (declining/ambiguous), behaviour is **unchanged**: the model's answers
  stand, as today.

Hand-derive the expected values before running (rule: never edit a literal to make a test pass), from synthetic
rows built in the tests: (a) `label | Yes | X | No` with `mark_follows_option` and a model reply selecting `No`
-> `answers == ["Yes"]`, `value_raw == "Yes"`, original in provenance; (b) the same row with no convention and
the geometry ambiguous -> unchanged; (c) `label | A | X | B | C` with the model selecting `B` -> `["A"]`; (d) an unmarked row -> unchanged;
(e) a `multi` row where the resolver selects two options -> both texts, option order; (f) a row the model got
right -> unchanged, no provenance note. A mutation test must fail if the override is dropped.

### B. No silent empty label (issue 4). Behaviour change.

When the label built from the cited `L=` cells is empty after `strip_marks`, never emit the field with an empty
label silently. Rule: if the row (the lattice row of the cited cells) has **exactly one** non-mark text cell
that is not otherwise cited as an option, answer or note, use it as the label and review-flag the field (use the
existing review channel the draft/record already has, `review=True` / `ambiguity`; read how the lines parser
sets `review` at `lines.py:517-569`); otherwise keep the field, leave the label empty, and review-flag it so it
is never silent. The text-as-answer case (`text L=27.0 A=27.1`) is covered by the same rule: the label is
repaired from the only non-mark text cell **and that cell is no longer also the answer** (decide, defend in the
note, and test; if you judge the answer should stay, say why).

Hand-derive and pin: `bool L=27.1 O=27.0` unchanged; `bool L=27.0 O=27.1` -> label `Enforce Unique Policy
Numbers` (synthetic text of your own; do not reuse any client wording), review-flagged; `text L=27.0 A=27.1` as
decided above; a row with two non-mark text cells and `L=` on the mark -> empty label, review-flagged, not
repaired. A mutation test must fail if the repair is dropped.

### C. A per-tab outcome in coverage (issue 1). Informational only.

Extend the per-tab coverage record (`TabCoverage`, `coverage.py`) so a caller can tell **"the model labelled
every row `hdr`/`note`/`skip`"** from **"anchors present but unbound"**: add `dispositioned` (the count of rows the model
returned a disposition for, field or not; the per-row `Disposition`s are produced at `resolve.py:328-337` and
collected through `dispositions_out` at about 1432 and 1687, but neither pipeline caller passes it, and a
`Disposition` carries no page, so per-tab attribution is a small API addition you must make and report), as an
`omit_if_default` field so `json` records stay byte-identical, plus a derived `model_declined` that is true when the tab has anchors, the model returned at least one disposition, and none
was a field. It must **not** change `InstanceStatus`, must not change `min_coverage` semantics, and must not
add a default error. Under `json` the field is `None` (the information does not exist). `SCHEMA_VERSION` stays "2"
provided `json` instance records are byte-identical (prove it with a test that compares a `json` run's
serialised bytes before and after); if they are not identical, stop and report what moves.

Tests (synthetic, scripted replies): all-`hdr`/`skip` reply -> `model_declined` true and status unchanged;
a reply with one field -> false; an empty reply (`end` only) -> decide and pin (an empty response is a
different failure; do not conflate); `json` -> `None`.

### D. A stray mark must not null a TEXT answer (issue 2). Behaviour change, narrow.

For a field of `control_type` TEXT, a mark cell in its row (or a marker injected from the row) must neither set
`ambiguity` nor null `value_raw`: `value_raw`/`value_normalized` follow `answers`, as they do for a text field
on a row with no mark. Scope the guard to TEXT only; SELECT/MULTI/BOOL decisions are **unchanged** (a
`convention_unsupported_by_geometry` on a select still stands). Before changing anything, write the
characterisation test through the real path (a Pipeline run with a scripted client, as the reviewer did) with
the glyphs `X`, `☒`, `✓`, with and without `mark_follows_option`, and watch it fail for the right reason.
Hand-derive: `X | label | answer` -> `answers == [answer]`, `value_raw == answer`, `ambiguity is None`, for
all six combinations; the select row beside it is unchanged (`Rounding | Yes | X | No` -> no convention:
`ambiguity between_options`, `value_raw None`; with convention: `Yes`); a TEXT row whose mark sits inside the
answer cell is unchanged. A mutation test must fail if the guard is applied to selects. State in the note what
a model reply must look like for the typed answer to bind. If the characterisation shows something other than
the chain described in verified item 4, stop and report.
