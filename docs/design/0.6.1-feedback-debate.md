## 0. Headline

- The "0 fields, status complete" tabs are not a resolver bug and not a status bug: data tables where the
  model chose `hdr`/`note`/`skip`. Keep status as is. Add an informational per-tab outcome.
- The signal is already computed and dropped: the lines parser returns per-row `Disposition`s
  (`resolve.py:328-337`, `1143-1166`, collected via the opt-in `dispositions_out`, `resolve.py:1432`,
  `1687-1688`) and neither pipeline caller passes it (verified: only those three references exist). This is

- Two real code defects are named by the brief (json `answers` contradicting the resolver's selection;
  empty `label_text` on lines). A third (issue 2, null value on mark+label+answer rows) is **disputed**.
- Everything else is docs.

## 1. Issue 1: lines, 0 fields, `complete`, `errors=[]`

Facts. The zero-fields guard (`pipeline.py:751-756`) fires only when `layout.hypotheses` is non-empty; a plain
data table has anchors but no ambiguous-control hypotheses, so it stays `complete`. `min_coverage`
(`pipeline.py:773-780`, range (0,1]) already sets PARTIAL when `ratio < min_coverage`; ratio is 0.0 on these
tabs, so `min_coverage=0.01` catches them today, and `record.coverage_min_ratio` (`pipeline.py:771-772`) lets
an integrator write their own rule. A draft that cites bad refs still becomes a `Field` with
`unresolved_source_refs` (`resolve.py:2232-2256`), so `fields == 0` on a tab means the model dispositioned or
omitted every row, it did not cite-and-get-dropped. A scripted valid reply (`text L=4.0 A=4.1`) binds, so
valid replies are not dropped.

Options.
1. Default PARTIAL on anchors-but-nothing-bound. Rejected (agreed): every workbook with a lookup/data tab
   would never be `complete`.
2. Documented `min_coverage=0.01` "strict tabs" recipe, no code. Adopt.
3. Informational per-tab outcome in `TabCoverage`. Adopt (below).
4. Per-tab json fallback in the library. Rejected (agreed); belongs to the integrator.

Decision on the shape (a concession by Claude). Claude proposed an opaque outcome enum; hearth argued, and
Claude accepts, for a **count** plus derived reading: add to `TabCoverage` a `dispositioned` count (rows the
model labelled non-field) as an `omit_if_default` member (precedent `model.py:267-272`, `599-605`), so the
three-way partition is derivable: consumed (`units_consumed > 0`), dispositioned (declined), neither (anchors > 0,
nothing consumed, nothing dispositioned = the genuine leak). The brief's `model_declined` bool may be added as a
convenience derived from the same data (true iff anchors > 0, at least one disposition, none a field); hearth's
synthesis was not obtained (round 4), so whether to ship the bool alongside the count is an owner question.
`None`/absent under json (the information does not exist).

Cost, stated honestly. `Disposition` has no page/tab (`resolve.py:335-337`); `rows` are per-chunk lattice
rows. Per-tab attribution means carrying the chunk's page from the collection site (`resolve.py:~1571/1580`)
into `Disposition`: a small API addition, not pure plumbing. `coverage.py`'s "no element text" contract
(`coverage.py:1-12`) is preserved (row indices only). It must not change `InstanceStatus`, `min_coverage`
semantics, or add a default error.

Why not a library json fallback (both agreed): the contract is a per-run token in the call-cache and instance
keys (`pipeline.py:587-603`, `600`) and the projections differ wholesale (`project_lines_chunks` vs
`project_chunks`, `pipeline.py:678-695`), so a fallback re-authors all tabs (zero call-cache hits), not three,
unless the integrator splits the workbook per tab. The outcome signal's real job is deciding whether to pay a
second pass at all; the docs should say the fallback is not selective.

## 2. Issues 3 and 4: where the brief and the debate converge

Issue 3 (json checkbox answers wrong at 0.95 vs lines right). Hearth's mechanism: on json the draft takes the
model's own `selected` (`resolve.py:1320`); on lines `options[].selected` comes from `A=` refs plus
geometry/convention (`resolve.py:906-911`), so the resolver decides. The brief found the sharper defect:
with `mark_follows_option`, the resolver overrides `selected`/`value_raw` correctly but **`answers` keeps the
model's claim, with no flag**. That is a likely cause of "4 of 4 wrong at 0.95" for an integrator reading
`answers`. Decision: the brief's Part A (answers agrees with the resolver's selection, original kept under
provenance, unchanged when the resolver declines) plus the docs "who decides marks" section. Hearth noted
`_selections_disagree` (`resolve.py:2175-2181`, geometric path `2394-2400`) already flags model-vs-geometry
disagreement as `AMBIGUOUS_MARK`; the docs should tell integrators to check that flag, and if it is absent the
mark was not injected into `source_elements`. Unverified: that the integrator's 4 rows hit this path (their
adapter is not ruled out).

Issue 4 (empty `label_text`). Two mechanisms, distinguishable on the emitted Field: (1) unresolved `L` ref
(`_ref_element_id` None, `resolve.py:816-819`; leaves `unresolved_source_refs` and a review flag); (2) a
resolved `L` cell that is only a mark or blank, so `strip_marks` yields `""` (`resolve.py:821-823`; no
unresolved ref, no review flag). A literal under `L` is a sentinel (`lines.py:38-39`, `142`), i.e. case 1.
Hearth hypothesised (2); the brief reproduced exactly (2) (`bool L=27.0 O=27.1`, `text L=27.0 A=27.1` on
`X | text`). Decision: the brief's Part B (never emit silently: repair from the only non-mark text cell and
review-flag, else keep empty and review-flag). Trap to test: `text L=<mark> A=<text>` must not leave the same
cell as both label and answer; the brief leaves that decision to the builder, defend it in the note.

## 3. Issue 2: DISAGREEMENT (unresolved, flagged for the owner)

Symptom: under lines, a row `mark | label | typed answer` returns the field with a null value, ~15-20 misses,
four prompt variants did not fix it.

- Brief (reviewer, scripted run): `text L=<label> A=<answer>` binds the answer; so the nulls come from the model
  emitting `single`/`bool` for the row, "not a resolver loss"; change no resolver code, add
  `test_characterise_*` tests only.
- Hearth (static reading, verified by Claude reading `resolve.py:2281-2356`): for a TEXT draft the marker can
  be injected into `source_elements` (`_injected_marker_refs`, `resolve.py:960-993`); the geometric/declared
  decision (`_geometric_mark_decision`, `2004-2076`) matches against `draft.options`, which is `[]` for TEXT, so
  an `auto_select`/`declared_convention` is downgraded to `declining` (`2296-2301`) and then
  `decision.kind in ("ambiguous","declining")` sets `value_raw = None` before the TEXT branch (`2345-2348`),
  discarding the typed answer and setting `AMBIGUOUS_MARK`. It also explains why no prompt variant helped and
  why `fix2_style` moved rows (it changes which markers get cited/injected). Hearth proposed guarding the
  geometric call for `ControlType.TEXT` (also covers kind-rule-derived TEXT, `resolve.py:1114-1117`, which clears
  options).

Why both can be true. The brief's run probably had no `checkbox_conventions`; the integrator ran
`mark_follows_option`. The hearth chain needs a mark to be injected and a decision to exist. Claude re-read the
code and could not rule the chain in or out without running it, and was told not to repeat the experiment.
Hearth was asked (round 4) for the sharpest firing condition and did not answer.

Position (Claude): this is a verifiable fact, so do not argue it, test it. Required before any resolver edit,
and consistent with the brief's Part D: the characterisation test for `mark | label | answer` MUST run through
`drafts_to_fields` **with `checkbox_conventions=[mark_follows_option]` and also without**, using a real glyph
(`layout.py:26-39` `_MARKS`; ASCII `[x]` never injects; the mark cell must survive
`_option_text_if_option_like`, `layout.py:245-256`), and assert `value_raw` and
`provenance.review_flag`. Falsifier: `value_raw is None` **with** `AMBIGUOUS_MARK` means the resolver nulled a
correct TEXT draft (N1, fix it); a plain decline or a `single`/`bool` control type with `answers == []` means
the model chose the kind (N2, keep the brief's stance). If N1 is shown, the narrow fix is TEXT-only (skip the
geometric path for TEXT), must not widen to BOOL/SINGLE/MULTI (a glyph is the control's state there), and rides
the same `PIPELINE_VERSION` "6" as Parts A/B (one re-pin, not two). If the test shows N2, nothing changes in
the resolver.

Json exposure of that fix is narrow: marker injection exists only in `_draft_from_record` (`resolve.py:933`,
lines path); the json path `_parse_one_draft` (`:1315`) does not inject. Still run the json sha pins; do not
reason them through.

## 5. Proposed 0.6.1 scope

Behaviour-changing (needs version thinking):
1. Part A: `answers` follows the resolver's selection (json and lines paths through `drafts_to_fields`).
   `PIPELINE_VERSION` "5" -> "6" (rule at `model.py:24-29`: bump iff a default-config run's fields change).
2. Part B: no silent empty label. Same bump.
3. (Conditional) issue 2 TEXT guard, only if the section-3 test shows N1. Same bump, same release.
4. Part C: `TabCoverage` count (+ optional bool). Additive and `omit_if_default`: hearth and Claude agree it
   does **not** need `SCHEMA_VERSION` "3" (K1 precedent, `model.py:373-374`, `599-605`; unaffected records
   serialise byte-identically) and does not need a pipeline bump by itself (fields unchanged). The brief
   implies "3" but hedges ("moves only if Part C requires it"); this is the disagreement to settle by actually
   checking that json records stay byte-identical. Caveat to document: an already-cached lines instance lacks
   the key until `force=True` or a bytes change (the instance cache is served, `pipeline.py:604-607`), and
   absent reads as "not measured".

Constants. Moves: `PIPELINE_VERSION` "6", package 0.6.1. Stays: `PROMPT_VERSION` "4" (no prompt change; do
not touch `PROMPT_VARIANTS` text), `KIND_RULE_VERSION` "2", `SCHEMA_VERSION` "2" (pending the byte check). No
new cache-key token. Pin sites hearth listed (hand-edit only literals and sha constants; treat the json record
sha guards as the measurement, not pins to re-baseline): `tests/test_060_prompt_variants.py` (~95-102,
563-565, 587-588, 604, 840-842), `tests/test_060_kind_rule.py:452`, `tests/test_label_not_option.py:240-242`;
also `tests/test_non_answer_columns.py:111-124` must stay green. Line numbers are hearth's and unverified by
Claude. The behaviour record is `CHANGELOG.md`; add the 0.6.1 entry with a "Read before you run it" line
(`PIPELINE_VERSION` moves, cached 0.6.0 instances are not served, what changes for `answers`).

Docs only: README "json vs lines" (speed as "one integrator measured", who decides marks, what `answers` and
`options[].selected` mean per contract, when to prefer lines: checkboxes dominate), "strict tabs"
(`min_coverage=0.01`, and that it also flags data/lookup tabs), a note that a json fallback is not selective;
README link to `CHANGELOG.md` and a `Changelog` URL in `pyproject.toml`; export `PROMPT_VARIANTS` from the
package root and name `formextract.pipeline.PROMPT_VARIANTS` in the docstring; reword `README.md:77`.

## 6. Owner questions (recommended defaults)

1. Run the issue-2 test with and without `mark_follows_option` before deciding? Default: yes, mandatory; fix

2. Ship the `model_declined` bool in addition to the `dispositioned` count? Default: yes, derived from the

3. `SCHEMA_VERSION` stays "2" for the coverage field? Default: yes, if json records are byte-identical; bump

4. Part B text-as-answer: when the repaired label cell is the answer, drop it from the answer? Default: yes
   (a cell is not both), review-flagged.
5. Part A: where does the model's original `answers` live? Default: existing `Field.provenance` shape; no new
   `Field` member.
6. One release for all (0.6.1) or docs+coverage first and resolver edits after? Default: one release, one
   `PIPELINE_VERSION` move (hearth: re-pinning shas twice costs more).

## 7. What must NOT be done

- Do not make "anchors but nothing bound" a default PARTIAL, add a default error, or change `min_coverage`
  semantics.
- Do not add a library-level json fallback or mix contracts in one run/cache key.
- Do not change a prompt or `PROMPT_VARIANTS` text, add a prompt variant, or bump `PROMPT_VERSION`.
- Do not change the resolver for issue 2 without the with/without-convention repro; do not widen any such
  fix beyond TEXT.
- Do not edit a gold/hand-typed literal or re-baseline a json sha to make a test pass; a moved json sha is a
  finding.
- Do not put the integrator's workbook, its cell text, or its wording in a fixture, test, commit or prompt.
- Do not add a cache-key token for the coverage field (the pipeline token is enough).
