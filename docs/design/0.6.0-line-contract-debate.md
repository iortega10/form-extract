# 0.6.0 line contract: outcome of the Claude / hearth design debate

Goal: decide the next model-facing output contract for form-extract: a
field-keyed, line-oriented, reference-only contract that replaces the planned
compact-JSON T5 of `0.6.0-plan-debate.md`, with a grammar concrete enough to
test, a coverage-as-constraint protocol, and a gold set that measures grouping
quality (not only speed) before the contract becomes the default.

Status: the outcome of a read-only design discussion, not a transcript. It
edits no source and makes no network or API call. It is the input to a build
spec and to the owner's decisions. It **supersedes T5 and part of T2/T6/G1 of
`0.6.0-plan-debate.md`** (section 9 says which); every other row of that plan
(T3/T4 landed, T7 chunking, T8) stands unless stated here.

Method. Claude (author) read `docs/design/0.6.0-plan-debate.md` and the code,
wrote a position per question (grammar draft, derivation rules, coverage,
gold set, versions) as the opening message so hearth did not lead, then argued

`form-extract/.hearth/sessions/` (resume with `--resume sa81afba7`). Round 3

## 0. Headline

1. **A reference-only line contract is worth building, but only behind a gold
   set.** The naive prototype cut output about 10x (1.7k tokens / 4.7 s vs
   19.7k / 73 s) and its quality was never judged. The gold set (G) is the
   first turn; the contract does not become the default on a speed number.
2. **Lines make the resolver derive what the model used to copy.** Label,
   option, annotation and text-answer strings come from the referenced elements'
   own text (identity, not text matching); the model states only kind,
   grouping, and an answer reference where no mark decides. This removes about
   85% of the JSON volume (source_elements 53%, options and selected 16%,
   region_id 8%, annotations 5%, confidence 2%) and, as a side effect, makes
   `field_id` independent of how the model paraphrases a label.
3. **Marks must be derived, or the grammar decides none.**
   `_geometric_mark_decision` only sees glyph ids that are in the draft's
   resolved source elements (`resolve.py:923-927`); a reference-only option list
   never names a bare `X` cell. The resolver therefore injects the markers that
   attach to a field's option cells. That makes the multi-marker defect T8
   (`right_only[0]`, `resolve.py:971-990`) **a prerequisite**, not an optional
   fix.
4. **Truncation and completeness become cheap.** A line cut loses at most the
   last line (drop it, re-ask it); a coverage unit with no line gets ONE targeted
   re-ask. The status default for the new contract is gated on measurement, not
   on a number tuned on one file.
5. **Layout hypotheses are not a proposal worth printing.** What they honestly
   hold is "which elements share a row". That is delivered by a new derived row
   view (the *lattice*), which is also the coordinate the model uses.

## 2. Verified facts the design rests on

All cited against the working tree.

- **The 0.5.0 contract and prompt**: `BINDING_OUTPUT_CONTRACT`
  (`resolve.py:47-54`), `build_prompt` (`:232-268`); each ref is an object
  (`:52`, `_parse_one_draft` `:403-447`). `PROMPT_VERSION = "3"`
  (`resolve.py:60`), `PIPELINE_VERSION = "3"` (`model.py:19`),
  `SCHEMA_VERSION = "2"` (`schema.py:11`).
- **The projection has no row coordinate.** `project_chunks` prints one block per
  region (`### region [type]`) and inside it `- band N: i=text | ...`
  (`resolve.py:196-212`); regions are per column (`layout.py:194-227`), so a
  label band and its value band in another column are in different blocks
  paired only by order. Verified.
- **But a band is already a whole row in contiguous xlsx.** Columns are split
  only at fully empty sheet columns (`layout.py:104-116` with the contiguous
  `col_x0/col_x1`, `xlsx.py:61-72`), so in the measured tab (105 bands for 98
  anchors, 9 regions) label, marks and options are segments of one band. The
  missing row coordinate bites with a gutter column or on PDF. Verified.
- **Bands are single-linkage and per column**: `_make_bands` updates
  `last_center` every iteration (`layout.py:139-152`), tolerance
  `0.6 * median(height)` (`:121, :633`). An xlsx merged cell has
  `center_y = (min_row - 1 + max_row) / 2` (`xlsx.py:101-109`), which for an even
  span is equidistant from two rows (both within tolerance at pitch 1.0), so a
  naive "group bands by y-centre" rule would fuse rows. Hence the lattice rule
  in section 3.6.
- **Anchors** are every `FIELD_ROW` band with a non-empty normalised label in the
  single densest FIELD_ROW column (`layout.py:534-599`); `FIELD_ROW` is the
  fall-through of `_band_type` (`:174`), so a mid-page section heading or a stray
  note becomes an anchor no field will use. Verified.
- **`layout.hypotheses`** (`layout.py:452-531`): one entry per `FIELD_ROW` band in
  EVERY column (loop `for col in sorted(bands)`, `:466-497`), so a two-column
  form lists each row twice, once per column as "label";
  `label_element_ids` is the whole band (`:488`); `value_element_ids` is every
  other-column element on the same row (y tolerance and a 3x height factor,
  `:471-480`); `control_guesses` is a token/glyph-count heuristic, a two-item
  `ambiguous` list unless it is a pure grid (`_control_guesses`, `:424-449`); the
  GRID entry finds its label by scanning a column to the left, then above
  (`:498-516`). It is read only by a diagnostic (`pipeline.py:642-645`) and
  `evals/structure_probe.py`. The prompt never shows it. Verified.
- **Marks**: `_geometric_mark_decision` considers only glyph ids among the
  draft's resolved source elements (`resolve.py:923-927`); a `RIGHT_ONLY` marker
  with exactly one candidate returns `auto_select` for `right_only[0]` only
  (`:943-949, 971-990`); `drafts_to_fields` then selects exactly that option
  (`:1224-1232`). `UNATTACHED` markers have empty candidate lists
  (`layout.py:411-412`); a marker only gets a classification inside a
  `FIELD_ROW` band (`:325`). The model's `selected` is consumed by exactly one
  check, the `auto_select` agreement test (`resolve.py:1280-1288`).
  `declared_convention` appends a token and is cross-checked by nothing
  (`:1289-1290`).
- **`field_id`** = hash of `(page, column, region_id, normalize_label(label),
  ordinal)` (`resolve.py:851-855, 1316-1318`); ordering inside a region is
  `_anchor_sort_key` (T4 tie-break, `:824-848`) keyed on the first ref in the
  draft's own region (`_anchor_band_id`, `:817-821`).
- **Replay**: `apply_binding` drops every ref whose `region_id` equals the draft's
  region as "the label element" (`reuse.py:62-64`). In a one-region layout the
  label band is the whole row, so a replayed TEXT binding loses its value ref and
  ends in `REPLAY_MISMATCH` (`resolve.py:1270-1276`). A latent defect today
  (`region_id` is model-stated, same hazard); section 4 fixes it.
- **Element already carries style**: `font`, `size`, `color`, `fill`, `sheet`,
  `merged` (`model.py:135-144`), filled for xlsx at `xlsx.py:117-127`. Bold and
  italic are missing. The PDF reader keeps only `font, size, color` and drops the
  span `flags` where bold lives (`pdf_text.py:43`, hearth's reading).
- **`LLMResponse` has no finish reason** (`resolve.py:69-75`: `text, model,
  params, tokens, latency_ms`).
- **Coverage today** (T4): units = anchor rows + GRID regions; numerator = any
  element of the unit's own band in a field's resolved `source_elements`
  (`coverage.py:52-82, 130-132`). It takes `fields`, so `hdr/note/skip` lines
  would be invisible to it.
- **Call cache** keys on `sha256(prompt) | model | params | purpose`
  (`store.py:186-201`, hearth's reading, re-checked by it); the instance key is
  `compute_cache_key` (`pipeline.py:241-284`), and `min_coverage` is appended
  only when set so default keys stay byte-identical (`:278-282`).
- **Existing eval harness** scores by label key and exact value equality
  (`evals/harness.py:97-131`) with integer PRF (`metrics.py:17-40`); it cannot
  score grouping.

## 3. The grammar

### 3.1 Projection (model-visible input)

One line per **row** of the page-global lattice (section 3.6), numbered top to
bottom, segments numbered across the row left to right:

```
12: 0=Do they ship to Canada? | 1=X | 2=Yes | 3=X | 4=No
13 [grid]: 0=AK | 1=AL | ... | 9=GA
14: 0=Confirm on vendor portal [annotation]
```

A row tag is printed only when not a plain field row: `[hdr]`, `[grid]`,
`[prose]`, taken from **the row's band in the anchor column if present, else the
row's leftmost band** (hearth: "most structured type" is not a total order). Tags
are projection hints only: there is no grid kind. The caller-declared
`[annotation]` segment tag stays as today (`resolve.py:209`). Region ids and
region aliases (`R<n>`) disappear from the model-visible text; the plan's
alias-order work is not built. The row id is a projection coordinate: it is
translated back to `(region, band, segment)` at parse time and **never survives
into `ElementRef`** (replay re-points by `(column, band_id)`,
`resolve.py:738-743`).

### 3.2 Response grammar (EBNF)

```ebnf
response = { noise | line } , [ endline , { any } ] ;
line     = kind , { SP , field } ;
kind     = "single" | "multi" | "bool" | "text" | "hdr" | "note" | "skip" ;
field    = key , ( "=" | ":" ) , items ;
key      = "L" | "O" | "A" | "N" ;
items    = item , { "," , item } ;
item     = ref | join | span | literal ;
join     = ref , "+" , ref , { "+" , ref } ;   (* ONE option / one run of elements *)
span     = ref , "-" , seg ;                   (* one option PER element, one row *)
ref      = [ "r" | "R" ] , row , ( "." | ":" ) , seg ;
literal  = '"' , { char - ( '"' | NL ) } , '"' ;  (* O and N only *)
row      = digit , { digit } ;
seg      = digit , { digit } ;
endline  = "end" ;
```

Semantics the grammar does not encode (they go in the prompt, the docs and the
parser tests):

- `L=` is required and, for field kinds, its elements are the label; `L=` on
  `hdr`/`note`/`skip` names the row(s) being dispositioned (no separate key).
- In `L`, `A` and `N` a comma **concatenates** (label spanning cells; several
  note cells). In `O`, a comma **separates options**.
- `O` is the exhaustive option-cell list: a span expands to every element, never
  abbreviates (hearth: marker attachment, section 4, is only sound if `O` is
  exhaustive). Elements in an `O` span whose `strip_marks` text is empty are
  marks, not options.
- **Cross-row ranges are not in the grammar**: `12.2-13.1` is a parse error that
  becomes a sentinel ref, never backtracked into a ref. A stacked control is a
  comma list `12.2,13.2,14.2`; a 50-option grid over several rows is one span per
  row.
- An element is never both `L` and `O`: `L` wins, the `O` occurrence is dropped
  and the field is review-flagged.
- `literal` is the explicit escape for text that has no element boundary (a
  single cell holding "Yes No"). Allowed under `O` and `N` only, never `L` or
  `A`; a literal option has no element and no bbox so it can only be selected by
  `A=` or a convention; a numeric `literal_items` stat reports how often models
  need it.
- Notes attach through the **field's** `N=`; a standalone `note L=5.0` is a pure
  disposition. A `cont` kind is cut: a field spanning rows lists several refs in
  `L`/`O`. A `grid`/`row` kind is cut (3.4).
- `A=` is optional when a glyph decides the field, required (single/multi/bool)
  when no glyph is among the field's elements. For `text`, the `A` elements are
  joined with a space into one answer.

### 3.3 Lexical leniency and totality (parser contract)

The parser is a pure total function `text -> (records, line_errors, stats)`:
it never raises.

- Case-insensitive kind and key; kind accepted by its first three letters
  (`sin mul boo tex hdr/hea not ski`); `L:` as well as `L=`; an optional `r`
  before a row; `.` or `:` as the ref separator; whitespace around commas.
- **Unknown kind** degrades to a review-flagged field (`ReviewReason.AMBIGUOUS_ROLE`):
  `single` when `O` is present, else `text`. It never raises.
- **A ref that does not exist** (bad row or segment, a cross-row range) becomes a
  sentinel `ElementRef` that fails the bounds check and lands in
  `unresolved_source_refs` with `UNRESOLVED_REFERENCE` (`resolve.py:1160-1169,
  1267-1269`), exactly as today. A line is a **record**, never a physical line
  fragment: literals cannot contain a newline.
- **Line vs noise** (hearth's rule, adopted): blank lines and markdown fences are
  noise; text before the first record or after `end` is dropped and counted
  (`noise_lines`); an unparsable line **between** records is a per-line error
  (`line N: ...`, like `field {idx}: ...` at `resolve.py:395-399`), which makes
  the run PARTIAL and leaves its row unbound for the re-ask. One bad line never
  fails the chunk. `end`/`END`/`end.` is normalised; it cannot clash with a form
  row labelled "End" because no text ever appears in a line.

tokenise separately), 1-2 per `key=`, 1 per comma and per kind word, and one
newline. They are not measured; the prototype's 1.3-1.8k tokens for 103-105
lines (about 13-17 tokens per line) is the only measured anchor, and it did not
use field-keyed grouping.

wide matrices; see risk 8.

### 3.5 Terminator, truncation, noise

The contract asks for a final line `end`. `LLMResponse` gains an optional
`finish_reason: str | None = None` (defaulted, source-compatible; the probe and
README client recipes fill it). Decision rule, in this order:

1. `finish_reason` normalised to a **recognised-cut** set (OpenAI `length`,
   Anthropic `max_tokens`, Gemini `MAX_TOKENS`) means cut; a **recognised-clean**
   set means not cut; **anything else is `unknown`** (a proxy may return `stop`
   after a hard cut) and falls to rule 2.
2. Terminator: `end` present means not cut.
3. Cut (by 1 or by absence of `end` under `unknown`): drop the trailing segment
   **iff** `text.rsplit("\n", 1)[-1].strip() != ""` (the tail after the last
   newline has content; hearth's refinement of "the last non-empty line").
   Record the error `response truncated after N lines`.
4. The dropped row is **force-included in the re-ask set** even if another field
   cited it (otherwise a cross-row citation hides the loss).

Why not "keep the last line if it parses": a cut `multi L=12.0 O=12.2,12.4`
(from `...,12.5`) parses and is silently one option short (hearth conceded and
withdrew the remedy). Why not the JSON path's structural test
(`resolve.py:287-343`): a line format has no depth or string state; the structural
detector does not transfer. Cost accepted: a model that forgot `end` and was not
cut loses at most one row, recovered by the re-ask; `end_missing` is a
diagnostic counter, not the trigger. There is **no repair call** in the lines
path (a line parser has nothing to repair); `CALL_BUDGET_PER_CHUNK = 2` becomes
one main call plus one re-ask.

### 3.6 The row lattice (L0)

Rows are a **derived view** over the existing bands: `layout.rows`, a list of
`(column, band)` lists per row, computed page-global **before any chunk split**
(so row N means the same in every chunk and in the re-ask), never persisted, no new
id space; identity stays region/band/anchor. Rule (hearth's fix to Claude's
"group by y-centre"): build the lattice from the **short bands only** (height
<= about 1.5x median; unmerged cells on xlsx), then assign every remaining band to
the row containing its **top edge** `y0` (tie to the smaller row). Top-edge
assignment never fuses rows, is reading-order natural and puts a tall merged label
on its top row deterministically. Invariant: every element is in >= 1 row.
Residual risk (section 12, risk 3): everything (identity, coverage denominator,
reuse fingerprints) now hangs on the lattice, so L0 is its own turn with a
fixture matrix.

**L0 built (2026-10-07).** The lattice is `formextract/rows.py` (new; stdlib
only; iterative — no recursion): `build_rows(layout, elements_by_id, *, page)` /
`build_all_rows`, a frozen `RowLattice` of frozen `Row`s, `SHORT_BAND_FACTOR =
1.5` recorded on the lattice. The row-grouping tolerance is the layout's own
**band tolerance** — `layout.py`'s local `tol_y`, a *local* (not a constant)
recomputed as `max(0.6 * median(element heights, default 1.0), 1e-6)` at
`layout.py:121`/`:633`/`:732`. `layout.py` is untouched and exports no tolerance,
so `rows.py` mirrors that single source (`_LAYOUT_TOL_FACTOR`); **this is the one
deviation from the build spec** (which said "import it") and it is flagged here.
Each `Row` carries `entries` — `(column, band_id)` in column x-order — and
`elements` in segment order; `row_of_element`, `segment(row, k)` and `ref_for(row,
k)` (a segment translated back to `(region_id, band_id, segment_index)`) are the
points the line contract will read.

Invariants tested over the (a)–(j) fixture matrix *and* every dev/held-out gold
tab: every element that belongs to a band is placed in exactly one row and once
within it; row indices are contiguous from 0 and rows ordered by top edge; the
lattice is stable under element-insertion order and under a reordered
`regions` list; `ref_for` round-trips through `layout.bands` for every element;
a merged tall cell lands on its top row and never fuses two short rows (verified
for odd *and* even span); two side-by-side controls share a row, a gutter layout
still puts label and controls on one row, and a two-cell stacked label stays on
two rows; cost is linear in bands (4,000 vs 8,000 synthetic bands, step ratio <
3, zero recursion).

**Gold: no finding.** Every dev and held-out field of the single-row structures
(`yes_no_row`, `dense_multi`, `text_field`, `typed_value`), every `side_by_side`
pair and every `stacked_multi` maps exactly as the lattice predicts —
`stacked_multi` puts the label on its own row and the options on the consecutive
rows below (the "label on the first row" of the block). Nothing is persisted: no
record byte changes; the existing suite passes unmodified.

### 3.7 L1a built (2026-10-07)

The parser is `formextract/lines.py` (new; stdlib only): `parse_lines(text, *,
finish_reason=None, steps=None) -> LineParse`, a pure total function that never
raises, never reads the layout and carries no state. Records are `LineRecord(kind,
line_no, label, options, answer, notes, review, unknown_kind)`; items are
`RefItem`, `JoinItem`, `SpanItem`, `LiteralItem` (module helper `item_refs`); a
ref is `SegmentRef(row, seg)` and `SENTINEL_REF = SegmentRef(-1, -1)`.

Decisions the spec left open, settled here:

- **Totality.** The parser never raises on any input (tested on a hostile corpus
  and 500 random strings). `_parse_fields` scans the tail of a line with a quote-
  aware brace-less lexer: a `+` token is a join (any bad part -> one sentinel
  ref), a `-` token is a span only when its right side is a bare `seg`, else a
  cross-row range -> one sentinel ref, never a line error.
- **Line errors are structural.** Only a missing kind word, a `key` not followed
  by `=`/`:`, an unknown key, or a record with no `L=` is a `line N: ...` error.
  A bad ref is a sentinel, not an error.
- **Noise vs error follows the spec's letter:** any unparsable line before the
  first *parsed* record is `noise_lines`, so a wholly-malformed response is all
  noise and `parse_lines` returns zero records (the status model reads that as
  FAILED). The same line between records is a `line N: ...` error.
- **Degradation.** An unknown kind becomes a review-flagged field
  (`LineKind.SINGLE` with an `O`, else `LineKind.TEXT`; `unknown_kind` keeps the
  model's word) and is never a line error.
- **Truncation (3.5).** `normalize_finish_reason` maps `length`/`max_tokens`/
  `max_output_tokens`/`max_completion_tokens` to `cut`, `stop`/`end_turn`/
  `stop_sequence`/`eos` to `clean`, everything else (including `None`) to
  `unknown`. A `cut`, or an `unknown` with no `end` and content, sets `truncated`;
  the trailing line is dropped (`LineParse.dropped_line`) only when it is a data
  line, and the error `response truncated after N lines` is always recorded on a
  cut.

`LLMResponse` gains `finish_reason: str | None = None` (defaulted,
source-compatible); `tools/live_probe.py`'s pipeline client now sets it from the
call's finish class, and the README client recipe fills it. No resolver, layout,
projection, prompt, cache key or record byte changes; the default output contract
is still `json`. 29 new tests (`tests/test_060_lines.py`); suite 332 -> 361.

### 3.8 L1a-fix built (2026-10-07)

A direct attack on the parser found eight defects; all are closed, with tests.

- **Not total on a huge digit run** (defect 1). `int()` on an unvalidated digit
  string raised `ValueError: Exceeds the limit (4300 digits)`. Now
  `_digits_to_int` is the module's only `int()` call: it requires ASCII digits and
  at most `MAX_DIGITS` (9) of them. Over-long and non-ASCII runs are
  `SENTINEL_REF`, never an exception, and `\d` (which matches every Unicode
  decimal digit) is not used anywhere.
- **Non-ASCII digits accepted** (defect 2). Arabic-Indic `\u0661\u0662.\u0660`
  and fullwidth `\uff11\uff12.\uff10` parsed as row 12 seg 0; the patterns are now
  `[0-9]`, so both are sentinels. Same for the seg-only span bound.
- **Digit-length cap** (defect 3). A 40-digit row is a sentinel, not a
  40-digit `SegmentRef`. `MAX_DIGITS = 9` covers a row and a seg; the cap is on
  the *digit string*, so no coordinate can be absurd.
- **Literals under `L`/`A`** (defect 4). The grammar allows a literal under `O`
  and `N` only. Under `L` or `A` a quoted token is now a sentinel item.
- **Unbounded spans** (defect 5). `O=14.0-9999999` was an expansion bomb; a span
  wider than `MAX_SPAN_WIDTH` (10,000), reversed, or cross-row is a sentinel. The
  span item is still never expanded here (the resolver expands it).
- **The review flag** (defect 4). A record is now `review=True` when it holds a
  sentinel, when a duplicate `O` occurrence of an `L` element is dropped (`L`
  wins, section 3.2), or when its kind is unknown; `unknown_kind` is unchanged. So
  the resolver can flag the field without re-scanning the items. A missing `L=`
  cannot produce a record at all, so it stays a `line N: ...` error, counted in
  `stats.no_label`, rather than a review flag.
- **Stats** (defect 6). `LineStats` now carries `lines_total`, `records`,
  `noise_lines`, `error_lines`, `literal_items`, `refs_total`, `refs_bad`,
  `end_seen`, `end_missing`, `truncated`, `dropped_tail`, `unknown_kind`,
  `no_label`, `empty_response` - definitions in the `LineStats` docstring; the
  original five names are kept.
- **Empty/noise-only responses** (defect 7). `parse_lines("")` and a
  fences-only response were reported as a truncation with nothing cut. An empty or
  noise-only response is now *not* truncated: `stats.empty_response` is set and
  the single error is `response empty` (the chunk is still PARTIAL). `truncated`
  is kept for a real cut: a `cut` finish, or an `unknown` reason with no `end`
  and with content.
- **Performance** (defect 8). The trailing segment is now classified (data line /
  `end` / fence / blank) and the cut decided *before* it is parsed, so a dropped
  tail costs one step, not one per item: a 10 MB single line is 9.1 s fully parsed
  and 0.011 s when dropped. `parse_lines` takes the repo's `steps` counter
  (`rows.py`'s `_ticker` style) for exact, clock-free cost assertions.

`LineParse.dropped` (a record) becomes `LineParse.dropped_line` (the 1-based
number of the dropped line), because the dropped tail is no longer parsed. Tests:
`tests/test_060_lines_hostile.py` (28 functions: a corrupted-input corpus with
exact outcomes, 1,000 seeded round trips through a test-only `render`, a ~2,900
input seeded fuzz with a planted-raiser anti-vacuity check, exact step counts and
a doubling ratio of 2.00 < 3, a static AST scan of the module, and ten mutation
cases each with the exists/reached/differs triple); suite 361 -> 418.

### 4.1 T8 built (2026-10-08)

The multi-marker defect is fixed in `resolve.py`; the allow-list was
`_MarkDecision`, `_geometric_mark_decision` and the `auto_select` consumers in
`drafts_to_fields`, plus the tests and these notes. No new public symbol and no
version constant moved.

**Reproduction (on HEAD `5aeedb0`, before the fix).** A hand-built stacked
multiselect — label row, then `X Option A` / `Option B` / `X Option C`, one field
citing all five cells — classified both markers
`RIGHT_ONLY` with a single candidate each, and the resolved field kept only
Option A: `assert [o.selected for o in field.options] == [True, False, True]`
failed with `[True, False, False]`. Through `tools/score_gold.py` the same defect
scored the gold `stacked_multi` tag `selected_ok 11 / 22` (the model's own
`selected` flags made the other half agree, so only half were flagged). After the
fix both are `22 / 22`. No existing test pinned the defect (the
`test_checkbox_states.py` cases are single-marker).

**The rule as built.** When a field's markers include one or more right-only
single-candidate markers and *no* BETWEEN and *no* COMPETING marker, the decision
selects the **union**: every such marker's single candidate option text, in
`draft_glyph_ids` order, de-duplicated by normalised option text (two markers
pointing at one option select it once), and every matched option is marked
`selected`. The BETWEEN and COMPETING short-circuits stay first and unchanged
(they still win even when the field also carries right-only markers). A single
right-only marker is byte-identical to before: the union of one is the old
`right_only[0]`, and the whole `Field` (including `field_id`) matches a
pre-fix expectation. In code the list rides on `_MarkDecision.option_texts` (with
`option_text` kept as its first element for the pre-existing consumers);
`_right_only_option_texts` is the collector, `_between_competing_short_circuit`
the two short-circuits, and `_selections_disagree` the model cross-check, so each
is a patchable seam the mutation tests use.

**Declining markers beside selectable ones.** A right-only marker whose single
candidate element is missing or whose `strip_marks` text is empty declines for
*itself* only: its id is recorded in `_MarkDecision.declined_marker_element_ids`,
it never cancels a selectable marker, and — because a marker that could not be
applied is still information for the reviewer — its presence forces
`provenance.review_flag` with `review_reason = AMBIGUOUS_MARK` even though the
union still selects the options it can. A field with only declining right-only
markers stays `declining`. The model's `selected`-flag cross-check now compares
against the whole union (it already compared the full selection set, so no extra
rule was needed): the model agreeing with the set is no flag; a subset or a
superset flags as before.

**Eval diff.** The canned `spec_fragment` manifest
(`python -m formextract.evals ... --llm canned`) is unchanged before/after:
region_type_accuracy `1.0`, regions PRF `0.833 / 1.0 / 0.909`, anchors F1 `1.0`,
binding F1 `1.0`, field_id_coverage `1.0`, mark_selection_accuracy `1.0`,
silent_selection_rate `0.0`. No multi-marker case exists in the bundled
manifests, as expected. Suite `418 -> 437` (`tests/test_t8_multimarker.py`).

### 4.2 L1b built (2026-10-08)

Status: **built and uncommitted**, all six parts. Suite `437 -> 456`: the only
existing test changed is
`tests/test_label_not_option.py::test_pipeline_version_is_in_the_cache_key`,
whose `PROMPT_VERSION`/`PIPELINE_VERSION` assertions moved `"3"` -> `"4"`; the

Parts: (1) projection and prompt, (2) the response -> drafts derivation,
(3) the authoring wiring, (4) config/version/cache key, (5) the offline
harness - `live_probe.py --gold --contract {json,lines}`, `make_gold.py
--canned-lines`, `tests/gold_lines.py`, (6) the test matrix. The default stays
`json`.

Decision as built:

- **Projection.** `resolve.project_lines_chunks` (new; `project_chunks` is
  untouched) prints one line per row of the page-global lattice
  (`rows.build_all_rows`), `"{row}: 0=a | 1=b"` with segments numbered exactly as
  `Row.elements` orders them, and a row tag taken from the row's band in the
  densest anchor column if present else the row's leftmost band, printed only
  when that band's region is not `FIELD_ROW`. No region id, band id or alias
  appears. The caller-declared `[annotation]` segment tag is preserved. The
  fallback chunk for a page with no rows mirrors `project_chunks`.
- **Prompt.** `resolve.build_lines_prompt` (new) states the 3.2-3.4 rules in
  model-facing prose and gives four invented worked examples (a Yes/No row, a
  dense multi, a grid with `N=`, side-by-side controls, a label spanning two
  cells with `A=`). No `[ctl?]` tag (default OFF, section 6).
- **Derivation.** `resolve.parse_lines_response(chunk, lattice, response, *,
  layout, elements_by_id, non_answer_element_ids) -> (drafts, dispositions,
  errors, stats)`, with a `Disposition(kind, rows, line_no)` record. One
  `BindingDraft` per field line, following section 4: label = `strip_marks` of
  the `L` cells joined in reading order; options = one per `O` element (`+` runs
  joined with a space, literals as written, an `O` element with empty
  `strip_marks` text is a MARK and not an option); annotations = `N` cells;
  the reading-order-first valid `L` cell gives `region_id` and the anchor band,
  and the `L` refs are placed first in `source_refs`; `A` cells are joined into
  `answers[0]` for `text` and otherwise are one answer each for the `A` cells
  not in the option set, and an `A` cell *in* the option set sets that
  `Option.selected` (the second opinion the existing cross-check reads); an
  `unknown_kind` record is review-flagged `AMBIGUOUS_ROLE`; `hdr`/`note`/`skip`
  produce no draft and are returned as dispositions; `confidence` is `None`.
- **Marker injection.** `_injected_marker_refs` attaches a marker classification
  to every field whose `L`/`O`/`A` cells contain the marker or one of its
  candidate cells (both clauses exclude non-answer ids) and appends the marker's
  `ElementRef` to `source_refs`, so `_geometric_mark_decision` sees it. In this
  codebase one element is one cell, so "any element of a cell that is a
  candidate id" reads the candidate id itself; the phrasing is kept for a future
  cell model. A marker shared by two side-by-side fields attaches to both and
  the BETWEEN/COMPETING short-circuit makes both `AMBIGUOUS_MARK`.
- **Bad refs.** `SENTINEL_ELEMENT_REF` (`region_id=""`, `band_id=-1`) fails the
  resolver's bounds check and lands in `unresolved_source_refs` with
  `UNRESOLVED_REFERENCE`, exactly as an unresolvable JSON ref. Nothing raises;
  every lookup is total.
- **Authoring.** `author_drafts` takes `output_contract` (default `"json"`),
  `layout`, `elements_by_id`, `non_answer_element_ids` and an optional
  `dispositions_out` collector; the lines chunk makes `LINES_CALL_BUDGET_PER_CHUNK
  = 1` call with `build_lines_prompt` and no repair, indexes the response only
  when it parsed with no line errors, was not cut and was not empty, and lists
  the `LLMCall` either way. `resolve_prompt` now takes a `validate` callable so
  the cache-miss check is the json parser on the json path and
  `_lines_response_ok` on the lines path. `chunk_workers`, `force`, T1 hygiene
  and the `draft.tab` carry all apply unchanged.
- **Replay.** `BindingDraft.answer_refs` (defaulted) carries a text field's `A`
  refs; `remap_drafts_for_page` remaps them like `source_refs`;
  `reuse.apply_binding` re-reads a replayed text answer from them when present.
  The json path leaves `answer_refs` empty and its replay rule is unchanged, so
  its outputs stay byte-identical.
- **Config, versions, cache key.** `PipelineConfig.output_contract` (default
  `"json"`, validated by `validate_output_contract`, `OUTPUT_CONTRACTS`).
  `compute_cache_key` appends one canonical `contract=<name>` token whenever the
  contract is not the json default. `PROMPT_VERSION` and `PIPELINE_VERSION` are
  `"4"`; `SCHEMA_VERSION` stays `"2"` (`answer_refs`/`review_reason` are
  defaulted). `Pipeline.run` builds the lattice via `project_lines_chunks` and
  passes the layout/elements/non-answer ids to `author_drafts`; coverage still
  consumes the resolved fields (L2a moves it to drafts + dispositions).
- **`declared_convention` cross-check (json included).** `drafts_to_fields` now
  runs the agreement check for a `declared_convention` decision as well as for
  `auto_select`, comparing the stated selection against the convention's option.
  A json run whose model marked an option different from the declared convention
  now carries `AMBIGUOUS_MARK`; no existing test pinned that, and the canned
  manifest declares no conventions.
- **JSON invariance.** `build_prompt`, `project_chunks` and
  `build_lines_prompt` are separate code paths; the json prompt and projection

**The offline harness (part 5).**

- `tools/make_gold.py --canned-lines DIR` writes `lines_<set>.json`: the perfect
  response per tab plus five line-level mutations, **in cell-id form**
  (`hdr L={Hold01!1:1}`). The generator may not import `formextract`, so it
  cannot know the `row.seg` a lattice assigns a cell; everything else in the

  first and field lines last, so the physical tail of a response is always a

- `tests/gold_lines.py` is the bridge: it ingests each gold tab, builds the

- `tools/live_probe.py --gold DIR --contract {json,lines}` (default `json`)
  threads the contract into `PipelineConfig.output_contract`, so the reviewer

**Offline acceptance, measured.** Strict identity is 1.0 on both sets: dev
`matched 244/244`, heldout `117/117`, `precision = recall = 1.0`, `merge_count =
split_count = missed = spurious = stray_ref_count = unresolved_ref_count = 0`,
`label_ok = label_total = 244`, `options_ok = 244`, `answer_ok = 64/64`,
`addressed 1140/1140`. The five line mutations move exactly the counters the
mutation table names (`drop_line`, `wrong_kind`, `merge_two` -> `merge_count 1`,
`split_one` -> `split_count 1`, `cut_before_end` -> one field per tab lost).

**Finding (needs the owner): the derivation cannot decide marks on a
multi-option band, so the lines contract loses selections the json contract
keeps.** `selected_ok` is `100/180` on dev and `57/91` on heldout, against
`180/180` for the json contract on the same gold and the same declared
conventions (measured with an equivalent canned json client). Per tag, the
lines path derives every mark of a *stacked* multi (`stacked_multi` 22/22, the
T8 case), every `matrix` (7/7) and every `typed_value` (11/11) selection, but
`dense_multi` 3/10, `grid_50` 0/10 and `yes_no_row` 37/70, with 42 fields left
`unexpected_ambiguous`.

Cause, exactly: (a) `layout._classify_markers` gives a mark in a spreadsheet row
**every** option-like cell to its right as a candidate (`right_ids` grows per
cell, `layout.py:353-379`), so a mark with several options to its right is
`RIGHT_ONLY` with `len(right_candidate_element_ids) > 1`; (b)
`_geometric_mark_decision` calls that class `competing` (`resolve.py:1649-1654`)
and its short-circuit returns that one decision, ahead of the right-only union
(`:1663-1665`); (c) `_apply_declared_convention` only converts a BETWEEN
decision (`:1783-1784`), so a `competing` mark keeps its ambiguity even when
`mark_precedes_option` is declared. The result is that a *single-row* Yes/No
control -- the commonest structure in the gold -- cannot have its mark derived
from geometry alone. The json contract never exposes this because a model states
`selected` itself and, on the json path, a model that cites no mark cell makes
`_geometric_mark_decision` return `None` (`:1640-1641`), leaving the model's
flags intact.

This is **not** an L1b defect to patch inside L1b: the fix is a resolver
semantics change (union the convention-eligible `competing`/`between` marks per
field, using each mark's nearest candidate on the convention's side), which the
turn table reserves to T8's own turn and its own eval diff, and L1b's stop line
is "default stays `json`". `tests/test_060_lines_gold.py` pins the numbers above
(`test_marker_rows_that_geometry_cannot_derive`), names the cause and is
cross-referenced here, so the gap cannot become silent and a fix must update the
pin deliberately. Recommendation: land that resolver fix as its own small turn
(T8b) before the owner reads the live gold run, since on this evidence the lines
contract is not yet shippable for a one-row Yes/No form.

**Also noted.** Option *order* on the lines path follows the model's `O=` list
(the json path's option order is the model's too), so only the option text
*set* is order-independent; the label, the anchor and `field_id` are the
document's and are stable across a model reordering its refs (tested).

## 5. Coverage as a constraint

### 5.1 Unit and disposition vocabulary

- **Unit**: T4's definition is reused: one per anchor row plus one per GRID
  region, after non-answer exclusion; `ratio = None` (ineligible, never a
  failure) when no unit survives (`coverage.py:85-92`). A tab with no anchors and
  no GRID: ratio `None`, no re-ask, status unchanged.
- **Consumption predicate for lines** is **row-level**: a unit is addressed when
  any element in the unit's lattice row(s) (all columns) is cited by any line.
  The json contract keeps T4's band predicate unchanged. Row-level is what makes
  side-by-side second labels and matrix cells reachable, and it makes a GRID unit
  neither vacuous nor unreachable (hearth found both failures under the
  band-only predicate).
- **Disposition vocabulary** (the lines that carry no field): `hdr`, `note`,
  `skip`. Counters per tab: `by_field` (a field line hit the unit, **this is
  `units_consumed`/`ratio` as today**), `dispositioned` (only hdr/note/skip hit
  it), `unbound`.
- **Honest meaning**: with `L=` required and the anchor band being the row,
  every field line addresses its own row. `addressed` therefore means "a line
  named this row", not "this row was mined". Docs say so; only the gold set
  measures mined.

### 5.2 Block additions (all defaulted, SCHEMA_VERSION stays 2)

`TabCoverage` gains: `dispositioned`, `unbound_after_reask`, `reask_calls`,
`reask_rows`, `skip_heavy` (numeric ratio `dispositioned / (addressed +
dispositioned)`, shown, not a status rule), `orphan_marks` + `orphan_marks_total`
+ `orphan_marks_truncated`, `noise_lines`, `end_missing`, `literal_items`;
`UnboundUnit` gains a defaulted `row`. Ids and counts only, never text.

### 5.3 Re-ask protocol

After parse and resolve, per chunk: the unbound units (plus any forced tail row,
3.5). If any exist, **at most one** re-ask call per chunk.

- **Sent**: the same instruction and contract, then only the unbound rows printed
  with their **global** row ids and tags, plus one neighbouring row each side
  marked `(context)` whose citations are discarded, plus "give a line for each
  listed row, or `hdr`/`note`/`skip` it; do not repeat other fields".
- **Budget**: `CALL_BUDGET_PER_CHUNK = 2` (main + re-ask); a transport failure is
  retried inside the existing attempt loop only; no second re-ask; leftovers stay
  unbound.
- **Different prompt, so not a deterministic repeat**: hearth first argued that
  temperature 0 reproduces the omission; that holds for the JSON repair call (the
  same prompt) and not for a shorter targeted prompt, which also cannot be cut by
  the same length limit. Hearth withdrew it.
- **Caching**: a normal call keyed by the exact prompt text (`purpose` may be
  `"cold_binding"` or `"reask"`); reruns are served from the call cache and cost 0
  tokens **only when the first response was archived indexed**. A truncated or
  field-errored first response is archived `index=False`, so a rerun re-sends it
  and the re-ask set can differ from the one that was paid for (risk 5). Counted
  in the cost report; never claim "no re-spend" without checking archive state.
- **A cover of < 10% of units** (the 5-of-98 case) makes the re-ask effectively a
  second full call: allowed, reported in `reask_rows`.
- **Determinism**: set and prompt are functions of the first response and the
  layout only.
- **Interaction with T4**: the json contract keeps T4 unchanged. For lines,
  `min_coverage` (numeric) compares **field-addressed / eligible** only (same
  meaning as T4, so contracts stay comparable); dispositioned units never enter it
  (hearth: otherwise the two knobs overlap) and enter only the default rule below.

### 5.4 Status model

| status | when |
|---|---|
| FAILED | ingest failure; or transport failure on all chunks; or the lines contract parsed **no record** on any tab that has units; or records parsed but **no field resolved anywhere** |
| PARTIAL | any line error or truncation error; a tab with units and **zero field-addressed units** (floor: a lazy model that `skip`s every row must not reach COMPLETE with an empty record); `min_coverage` set and a tab below it (as T4); the default gate below, if enabled |
| COMPLETE | otherwise |

**Default gate (gated on measurement, owner decision)**: record-level
`sum(unbound_after_reask) / sum(eligible_units) <= epsilon` (hearth: a per-tab 0/1
statistic fails a 40-tab form for one misclassified heading, which `_band_type`
guarantees happens). No numeric default is shipped: Claude proposed 1.0 and hearth
rejected it (section 12), because `FIELD_ROW` is the fall-through. The status rule
is **off** in the first lines release (`max_unbound_ratio=None`), the block always
reports; the owner pre-registers `epsilon` (suggested 0.02) and `delta` (a
`skip_heavy` bound, suggested to be read rather than enforced) **before** the live
gold run (G-gate), then reads the run against them.

## 6. Layout hypotheses as proposals

What `layout.hypotheses` can honestly propose today is **row co-membership** and
nothing else (verified inventory in section 2). Its `label_element_ids`,
`value_element_ids` and `hypothesis_id` are superseded by the lattice and must not
survive as a second ordering authority; `control_guesses` is an ambiguous two-list
heuristic. **Decision**: print no hypotheses and no accept/edit syntax in this
release. The model sees the lattice and the `[hdr]/[grid]/[prose]` tags.
**Disagreement-lite (section 11)**: hearth would also print a per-row control
ambiguity tag (`ambiguous = len(guesses) > 1`, `layout.py:494`, e.g. `[ctl?]`) as a
deterministic signal geometry knows and the model cannot; Claude would hold it
back (anchoring, one more variable). Settled by the gold set, not by argument:
**two A/Bs, not one**: (i) projection shape (rows vs the 0.5.0 bands/regions) with
tags off; (ii) tags on/off with the lattice fixed. A wrong tag anchoring the model
is measured by grouping precision/recall on the gold set, not by speed.

## 7. The gold set (G)

### 7.1 Construction

- `tools/make_gold.py`: openpyxl only, **never imports `formextract`**, seeded
  (`--seed`, `--tabs`), in the style of `formextract/evals/synthetic.py` (there is no `tools/make_fixtures.py` in this repo) and the evals
  synthetic family. Writes `.xlsx` tabs plus a gold JSON keyed by xlsx element ids
  `Sheet!r:c` (`xlsx.py:120`), so ground truth is independent of bands, regions and
  of any model.
- **Gold field** = `{kind, label_cells, option_cells, answer_cells,
  annotation_cells}`; **gold dispositions** = `{hdr|note|skip cells}`. Gold knows
  the text it wrote into each cell, so the scorer may compare derived text.
- **Tabs (dev: 12, held-out: 6, other seed and vocabulary)**, each 6-25 rows,
  together about 150 dev fields: plain Yes/No rows; dense multi-select; stacked
  multi-select; side-by-side controls; label spanning two rows and two cells;
  text field; typed-value field; no-glyph answer (bold, colour, typed "Yes"; xlsx
  only, section 8); 50-option grid; matrix (shared header); headers, notes and
  skip rows; merged tall cells; a gutter-column variant of the same rows (the
  case where bands are not rows); non-answer columns. Per structure tag the
  counts are small (about 6-12 instances); the scorer reports counts with
  percentages and never a bare percentage. More seeds scale it.

### 7.2 Scoring (exact; no half credit)

Hearth rejected Claude's "Jaccard over label+option cells >= 0.5 counts half"
with a worked counterexample: a side-by-side pair merged into one field scores
`J = 2/4 = 0.5` against each gold field, i.e. 1.0 total, fully hiding the merge;
a label spanning two rows predicted with one row also scores half; fractions
cannot enter integer PRF (`metrics.py:35-40`). Adopted rule:

1. **Identity**: a predicted field matches a gold field iff `set(L elements) U
   set(O elements)` are equal **and** kind is equal. Roles A, N and marks never
   enter identity. Because `Field.source_elements` is flat (`model.py:269`), the
   predicted set is first **intersected with cells whose gold role is L or O**;
   ids outside the gold cell universe are counted as `stray_ref_count` and never
   enter the identity set (one hallucinated id must not hide an exact match);
   `unresolved_ref_count` is reported separately. Anchor-set identity (hearth's
   first form) was corrected: a side-by-side second label is not an anchor
   (`layout.py:534-599`), so identity is the element set.
2. **Reported numbers**: strict field precision and recall; `merge_count` (a gold
   set is a strict subset of one predicted set); `split_count` (a predicted set is
   a strict subset of one gold set); on matched pairs `label_ok` (derived label
   text equals the text the generator wrote), `options_ok` (option text set),
   `selected_ok`, `answer_ok`; `disposition_acc` (gold hdr/note/skip cells hit by a
   disposition line); the `addressed` ratio labelled **perception** coverage; all
   per structure tag. The side-by-side tab encodes the **expected** `ambiguous`
   outcome where two fields share a competing marker, otherwise G would report a
   by-design regression.
3. The scorer works on **record JSON dumps** (stdlib, imports nothing), so it can
   be used on the owner's workbook as integers only.

### 7.3 Offline and live

- Offline: the generator also writes **perfect** canned lines (strict 1.0
  required of L1b) and the mutations of section 1 with the expected counter
  moves, so the scorer is tested. JSON baselines are canned too.
- Live: `tools/live_probe.py --gold` prints numbers only (the existing fixed
  numeric dict, `live_probe.py:393-419`); the json baseline is **re-run on the same
  gold set under the same versions** (a `PROMPT_VERSION` bump invalidates a stored
  baseline).
- **Overfitting**: prompts and few-shot lines are tuned on dev only; held-out is
  reported once per prompt version and never fed back; examples are written by hand
  from a different vocabulary than the gold fixtures; the owner's private gold is a
  third stratum never used for tuning.
- **Private gold**: same JSON schema, hand-labelled by the owner on the real
  workbook, stored under `local-private/` (git-ignored, `.gitignore`), scorer prints
  integers only.

### 7.4 G / G-gate built (2026-10-07)

Implemented and tested; the debate's owner question 1 (pre-registration of the

**Gold JSON schema** (`tools/make_gold.py`, `GOLD_VERSION = 1`):

  names in order), `cells`, `fields`, `dispositions`.

  hdr|note|skip`. `text` is exactly what the generator wrote (a marker cell's

**Tag vocabulary** (`FIELD_TAGS`): `yes_no_row`, `dense_multi`, `stacked_multi`,
`side_by_side`, `label_two_rows`, `label_two_cells`, `text_field`, `typed_value`,

`non_answer_column`; (`DISPOSITION_TAGS`): `header_row`, `note_row`, `skip_row`
(stored as `hdr`/`note`/`skip`).

**Sets.** dev: seed `20260101`, 12 tabs, 125 fields, 780 cells (each field tag
≥ 6 instances; `header_row` 12, `note_row` 6, `skip_row` 6). held-out: seed
`20260202`, 6 tabs, a disjoint label/option vocabulary (asserted empty
intersection).

**Scorer counters** (`tools/score_gold.py`, stdlib only, output numbers/tags
only): `gold_fields`, `predicted_fields`, `matched`, strict `precision`/`recall`
(no half credit; `null` on a zero denominator), `merge_count` (a predicted field
strictly contains a gold identity set), `split_count` (a gold identity set

`options_ok`, `selected_ok`, `answer_ok`, plus `addressed` (perception), all

### 7.5 G2 / G-gate built (2026-10-08)

- **Mixed tabs.** `Dev13..Dev16` and `Hold07`/`Hold08` (appended, fed by a
  separate RNG stream) place 9+ structure kinds in 60-100 rows each and always
  carry a 50-option grid block and a 12-row yes/no run; their fields carry
  `mixed_tab` **in addition to** their structure tag. Dev is now 16 tabs / 244
  fields. The homogeneous tabs stay byte-identical (a committed sha256 table in

  lists `homogeneous_tabs`/`mixed_tabs`.

  `{"tab": <name>, "anchor_pattern": null, "convention": "mark_precedes_option"}`

- **`Field.tab` fix (the one package change in this increment).** `BindingDraft`

- **Owner's open question (unchanged).** Pre-registration of the status
  thresholds `epsilon`/`delta` is still the owner's; not chosen here.

## 8. Later items (style, structural reuse, chunking)

**Style capture (S, later).** `Element` already carries font name, size, colour and
fill (`model.py:135-144`, `xlsx.py:117-127`). Add defaulted `bold` and `italic`
(openpyxl `Font.bold/italic`); `_decode` ignores unknown keys (`model.py:538`) so old
data loads; `content_hash` hashes raw file bytes (`store.py:25-30`) and the reuse
signature is integer-only geometry (`layout.py:711-770`), so the field is cache
neutral. Not printed and not used in resolution in 0.6.0. **Scope is xlsx only**: the
PDF reader drops span flags (`pdf_text.py:43`), so a PDF has no style ground truth;
either capture `flags` or declare it xlsx-only. A style-marked-answer tab exists from
G so a later `A=` cross-check (model vs style/glyph disagreement -> review reason) has
ground truth.

**Structural reuse with delta calls (U, after G and L3).** Compatible with lines
because labels and options are **derived from the target tab**, which also answers
hearth's "same-count option reorder" hole: a replayed line's refs are positional, so
option text and selection come from the target cells, never from the exemplar.
Alignment by position over the lattice using row fingerprints (segment counts, glyph
positions, merged flags, row tag), quantised to the banding scale
(`0.6 * median height`, `layout.py:121`); label text is **not** used for alignment.
Replay a line only if the target row's fingerprint equals the exemplar row's and every
cited `(row, seg)` exists; unmatched or changed rows go to ONE delta call carrying only
those rows. **Cache key**: the delta call is a normal call keyed by the exact prompt it
sends (hearth: mixing the exemplar key in breaks byte-identical hits), optionally
`purpose="delta"`; replayed rows need no call and are marked `replayed`, excluded from
`addressed` (risk 2). Today's page-keyed exact reuse (`pipeline.py:384-403`) is the
guard until then.

**Chunking trigger (K, contingent).** Cut the lattice at a **group boundary**, not just
a "no spanning band" row: a grid's label row and its option rows are separate rows, so a
band-only rule would split a grid from its label; use a `region_id` change (regions
already group consecutive same-type bands, `layout.py:194-227`). The trigger is **projected
line count or value-cell count**, not the anchor count (anchors come from one column,
`layout.py:573-576`, so a small label column with a huge grid under-reports output).
Measured trigger only: post-lines latency of the largest tab over a threshold, or
truncation or post-re-ask unbound on large tabs. The plan's other T7 rules (owned rows,
default `None`, cache key, guard against reuse) carry over.
