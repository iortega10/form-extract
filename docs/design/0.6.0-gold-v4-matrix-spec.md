# 0.6.0 gold v4: a real mark grid for the `matrix` tag (G4)

Status: spec for one build turn, **owner sign-off pending on the ground-truth change**. Author:
reviewer session, 2026-10-08. Builder: hearth. Do not start before the owner says go.

## Why

Live dev runs score `matrix` 0 of 7 under every prompt variant (base, fix1, fix2), grouping included
(`matched_ignoring_kind` is also 0). The cause is the gold, not the model. All three matrix builders
(`_tab_matrix_and_merged` Dev11, `_blk_matrix` in the mixed tabs, `_tab_hold_grid_matrix` Hold05)
write ONE header cell (`s.words.header()`, the same word pool as a section header, role `option`)
and, per row, a label plus a **typed value** under it (role `answer`). The field is
`kind=single, option_cells=[header], answer_cells=[typed value]`. Nothing on the sheet says the
header is an option or that a typed value is an answer to a single choice; the model reads the
header as a section heading and the typed value as the option, which is a reasonable reading. The
tag as built measures a convention nobody can infer.

(Correction to an earlier review note: `grid_50` is a label over a 5x10 block of options, not a mark
grid, so it does not cover this case.)

## What v4 builds

A matrix in the ordinary sense: a **header row of K column options** (K = 3, plain option words from
the set's option pool, not header words), and per row a label in column 1 and **one mark cell
(`MARKER`) under exactly one of the K headers**, the others blank.

Gold per row: `kind=single`, `label_cells=[label]`, `option_cells=[the K header cells]` (the same K
cells on every row of that matrix), `selected_option_cells=[the header above the mark]`,
`tags=["matrix"]` (plus `_MIXED_TAG` in a mixed tab), `kind_cue` and label wording unchanged
(`choose_one`). The mark cell is role `marker`, written with `Sheet.put(..., "marker")` like every
other mark. The scorer's identity is label + option cells, unique per row because labels differ;
verify it with the assertion below instead of assuming it.

**Resolver limit, recorded not fixed.** The resolver associates a mark with an option it is adjacent
to (`checkbox_conventions`, marker left of option). A mark in the label's row under a column header
has no convention, so the resolver should report the selection as undecided. Set
`expected_ambiguous=True` on every v4 matrix field (the designed outcome, exactly like the existing
`expected_ambiguous` fields) and **verify empirically** with a perfect-response run that
`selected_ambiguous_expected` rises by the matrix field count and `unexpected_ambiguous` does not.
If the resolver instead decides it, report what it decided; do not change the resolver. Whether
`unexpected_ambiguous` (36 to 41 on every live dev variant) is partly this tag is a hypothesis for the
turn to confirm or refute from the data, not a finding.

## Versioning (the part that is easy to break)

- Add `4` to `GOLD_VERSIONS`. Keep `GOLD_VERSION = 3` as the default this turn: v4 is opt-in via
  `--gold-version 4`; the owner flips the default after reading live numbers.
- v2 and v3 must stay **byte-identical**: the three builders branch on the set's gold version, the
  v2/v3 branches are untouched code paths, and the existing `OLD_TAB_SHA256` and `V3_TAB_SHA256`
  tables pass unchanged. Never edit a row of either table.
- v4 gets its own `V4_TAB_SHA256` (dev Dev01 to Dev16, held-out Hold01 to Hold08) and a test beside
  the v3 one. Only tabs that contain a matrix may differ from v3's bytes; assert that the others are
  byte-identical to v3. Be careful that the v4 builders draw from the RNG in a way that does not
  shift later tabs more than necessary; if tabs after a matrix move, say so in the outcome note.
- Per-tag field counts in v4 equal v3's (same number of matrix rows per tab: 6 in Dev11, the mixed
  blocks' `n`, 3 in Hold05). Dev and held-out vocabulary pools stay disjoint (existing test).
- Record in the manifest/gold JSON `gold_version: 4`; `tools/live_probe.py --gold` already refuses a
  directory whose tabs no longer match the manifest sha256, so it works unchanged.

## Tests (hermetic)

- v2/v3 hash tables unchanged and green; `V4_TAB_SHA256` pinned; non-matrix tabs equal v3's bytes.
- In a v4 set every matrix field has K >= 2 option cells, all in one header row above every label of
  that matrix; exactly one `marker` cell per row, in the column of the selected option's header;
  `expected_ambiguous` is true; label cue/wording equal to v3's.
- The scorer: a perfect response scores strict 1.0 on a v4 dev and held-out set (extend the existing
  `test_perfect_lines_reach_strict_one_on_dev[...]` parametrisation with v4, including the canned
  lines writer `--canned-lines`, which must emit a correct perfect response for the new shape). Assert
  `len({(f["tab"], frozenset(f["label_cells"] + f["option_cells"])) for f in fields}) == len(fields)`
  so a duplicate identity fails loudly. If you see a negative `kind_confusions`, that is this
  invariant breaking; add the same assertion to `score_gold.Gold.__init__` only if the owner agrees
  (separate finding, not in scope).
- `rows.py`, the resolver, the prompt variants, `score_gold.py` logic: untouched.
