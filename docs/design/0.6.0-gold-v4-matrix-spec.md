# 0.6.0 gold v4: a real mark grid for the `matrix` tag (G4)

Status: spec for one build turn, **owner sign-off pending on the ground-truth change**. Author:
reviewer session, 2026-10-08. Builder: hearth. Do not start before the owner says go.

## Why

Live dev runs score `matrix` 0 of 7 under every prompt variant (base, fix1, fix2), grouping included
(`matched_ignoring_kind` is also 0). The cause is the gold, not the model. All three matrix builders
(`_tab_matrix_and_merged` Dev11, `_blk_matrix` in the mixed tabs, `_tab_hold_grid_matrix` Hold05)
write ONE header cell (`s.words.header()`, the same word pool as a section header, role `option`)
and, per row, a label plus a **typed value** under it (role `answer`). The field is
`kind=single, option_cells=[header], answer_cells=[typed value]`. Nothing on the sheet says the
header is an option or that a typed value is an answer to a single choice; the model reads the
header as a section heading and the typed value as the option, which is a reasonable reading. The
tag as built measures a convention nobody can infer.

(Correction to an earlier review note: `grid_50` is a label over a 5x10 block of options, not a mark
grid, so it does not cover this case.)

## What v4 builds

A matrix in the ordinary sense: a **header row of K column options** (K = 3, plain option words from
the set's option pool, not header words), and per row a label in column 1 and **one mark cell
(`MARKER`) under exactly one of the K headers**, the others blank.

Gold per row: `kind=single`, `label_cells=[label]`, `option_cells=[the K header cells]` (the same K
cells on every row of that matrix), `selected_option_cells=[the header above the mark]`,
`tags=["matrix"]` (plus `_MIXED_TAG` in a mixed tab), `kind_cue` and label wording unchanged
(`choose_one`). The mark cell is role `marker`, written with `Sheet.put(..., "marker")` like every
other mark. The scorer's identity is label + option cells, unique per row because labels differ;
verify it with the assertion below instead of assuming it.

**Resolver limit, recorded not fixed.** The resolver associates a mark with an option it is adjacent
to (`checkbox_conventions`, marker left of option). A mark in the label's row under a column header
has no convention, so the resolver should report the selection as undecided. Set
`expected_ambiguous=True` on every v4 matrix field (the designed outcome, exactly like the existing
`expected_ambiguous` fields) and **verify empirically** with a perfect-response run that
`selected_ambiguous_expected` rises by the matrix field count and `unexpected_ambiguous` does not.
If the resolver instead decides it, report what it decided; do not change the resolver. Whether
`unexpected_ambiguous` (36 to 41 on every live dev variant) is partly this tag is a hypothesis for the
turn to confirm or refute from the data, not a finding.

### What the resolver did with a mark under a column header

`expected_ambiguous` holds on a perfect-response run — but not through the mechanism the existing
expected-ambiguous fields use. A v4 mark sits in the label row at the same column as the header one
row above it. The layout classifies every such mark `MarkerClass.UNATTACHED` with an **empty**
candidate set (`cand []`, `left []`, `right []`; the candidate search is same-row only, so a header
one row up is never a candidate). `_injected_marker_refs` therefore never attaches it to the field
(`visible & candidates` is empty and the mark is not itself cited), and `_geometric_mark_decision`
returns **no decision at all**: the predicted matrix field has all three options `selected=None`,
`value_raw=None`, `ambiguity=None` and **no review flag** (it is not even `AMBIGUOUS_MARK`). The
resolver does not "report the selection as undecided" with an `ambiguity` object; it simply sees no
mark.

That is still enough for the scorer, because the gold flag short-circuits the branch. On the perfect
dev run **`selected_ambiguous_expected` rises 10 -> 17 (+7, exactly the matrix field count) and the
`matrix` tag itself contributes 0 to `unexpected_ambiguous`.** Held-out: 6 -> 9 (+3). A perfect
response reaches strict 1.0 on both sets — `test_perfect_lines_reach_strict_one_on_dev[v4]`,
`test_perfect_lines_reach_strict_one_on_heldout[v4]` and the `--canned-lines` round-trip
(`test_canned_lines_artifact_round_trips[v4]`) are all green, with `matched == gold_fields == 244`
(dev) / 117 (held-out).

### Did tabs after a matrix move?

No. v4 differs from v3 in exactly the three tabs that themselves hold a matrix — `Dev11`, the mixed
`Dev13`, `Hold05` — and is byte-identical everywhere else
(`test_v4_leaves_non_matrix_tabs_byte_identical_to_v3`). Each tab (including each mixed tab) draws
from its own seed-keyed RNG stream, so a rebuilt matrix builder cannot perturb a tab that does not
run one; there is no cross-tab coupling to shift.

What *does* move is the blocks **after the matrix inside its own tab**: the v4 matrix block consumes
a different number of RNG values than v3's (a `words.options(3)` draw plus a per-row `randint`,
against one `words.header()` plus a `typed_value()`), so the mixed `Dev13`'s later blocks re-drew.
This is visible in the resolver data: on the v4 dev perfect run `unexpected_ambiguous` moves **42 ->
44** (two of Dev13's affirm/dissent rows flip from selected-ok into the competing case) and overall
`selected_ok` 100 -> 98. That +2 is *not* the tag — the `matrix` tag's own `unexpected_ambiguous` is
0 in both v3 and v4 — it is the within-tab RNG shift. Held-out is unaffected (`unexpected_ambiguous`
stays 18: Hold05's matrix is its last block and Hold07/08 hold no matrix). The dev selection pins in
`tests/test_060_lines_gold.py` are version-aware as a result. Removing even this within-tab shift
would require the v4 matrix block to consume exactly v3's RNG count, which `words.options(K)`
(variable-length `_distinct`) does not guarantee.

### Surprising / worth flagging

- **The resolver does not flag the header-column mark at all** (no `Ambiguity`, no `AMBIGUOUS_MARK`
  review flag). `expected_ambiguous` here encodes "the gold knows the resolver cannot derive this",
  not "the resolver reported an ambiguity". A future resolver-side cardinality/marker rule (the
  kind-confusion debate's lever) would therefore get no signal from the existing ambiguity object on
  this shape — it would have to run on the `UNATTACHED` classification directly.
- **`MarkerClass.UNATTACHED` is the whole story**: the candidate search never looks one row up, so
  the header directly above a mark is invisible. Worth recording next to the "marker left of option"
  convention.
- **`matrix` is still 0-for-7 live.** Strict 1.0 on a perfect response only proves the v4 gold is
  self-consistent and inferable, not that the model will read it; that is the reviewer's paced probe
  to settle.
- **No negative `kind_confusions`**: the id set is unique per v4 row, asserted in
  `test_v4_matrix_is_a_header_row_of_options_with_one_mark_per_label`
  (`len({(tab, frozenset(label_cells + option_cells))}) == len(fields)`).
- The `matrix` K is fixed at 3 (`MATRIX_OPTIONS`); the spec only asked for K = 3.
